# ローカル直接実行の最小ゲート

## 方針

Codex CLIは利用者のローカルディスク上で直接実行する方式を標準とする。Docker、VM、専用Windowsユーザーは必須にせず、将来の任意の隔離方式として扱う。利用者はローカル実行に残るリスクを受容する。

オーケストレーターは、Agentの実行条件と制御を保証する。Agentの判断結果および実行環境に残るリスクは、利用者の責任範囲とする。

この保証は、オーケストレーターが指定したsandboxモード、役割別実行環境、呼び出し回数、時間上限、停止条件を適用することを指す。契約の作業範囲・許可操作をAgentへ伝えることやCodex workspace sandboxは、OSレベルの完全なアクセス制御を意味しない。OSの実測隔離を完了条件には置かず、残存リスクを明記する。

## 実行ゲート

実Codex CLIを起動する前に、次を満たす。

1. 対象は破棄可能なコピーとし、契約の `workingDirectory` にその絶対パスを指定する。通常の作業checkoutや実データを直接対象にしない。
2. 実行契約で目的、対象範囲、除外範囲、許可操作、停止条件、時間上限を明示する。これらはAgentへ与える指示であり、OS隔離の証明ではない。
3. Implementerには `workspace-write` を、Reviewerには固定差分を配置した別の一時ディレクトリ上で `read-only` を設定する。
4. ImplementerとReviewerに別々の使い捨て `CODEX_HOME` とHOME系環境ディレクトリを割り当てる。親プロセスから許可した環境変数だけを渡し、既定profileや既存認証のコピーを使わない。
5. ImplementerとReviewerはそれぞれ最大1回。失敗時の再試行、自動修正、PR作成、mergeへ進まず、人間判断待ちで停止する。
6. timeout、停止要求、プロセス終了確認、出力stream切断を区別して記録する。終了状態が不明、証跡が不完全、永続化に失敗した場合は成功とみなさず停止する。
7. 本ゲートと具体的な実行範囲を説明した後、実Codex CLI起動について別途明示承認を得る。`--help`、`--version`、loginを含め、承認前にCLIを起動しない。

## Issueとの関係

- [ateliers-workspace Issue #11](https://github.com/Ateliers-Dev/ateliers-workspace/issues/11) の旧VM/OS隔離を実Agent起動の必須条件とする前提は、この方針には適用しない。役割別profile、環境変数の分離、停止、終了、証跡の各要件は、ローカル方式で実装・検証可能な範囲を維持する。通常profileの完全なOSレベル非到達性や全ファイル前後スナップショットはこの最小ゲートの必須条件にしない。
- Issue #11のWindowsパス別名、junction/symlink、TOCTOUについて既存のFake/単体検証は継続する。ただしそれをホスト全体の隔離保証と表現しない。既知の検証限界を報告する。
- Issue #4の永続化不整合は限定PoCで条件付き許容とするが、永続化不完全時は成功扱いしない。
- Issue #5（専用Windowsユーザー隔離）は任意の将来方式として維持し、Docker/VM等との選択肢を今後評価する。
- Issue #6（APIキー認証）とIssue #7（金額上限・予算制御）は後続必須機能として維持する。Issue #7は理論設計とFake/モック検証が対象で、実課金、自動チャージ、実際の上限到達を検証しない。
- 実Codex CLI、ChatGPT認証、モデル呼び出し、実課金・利用枠消費はこの変更で実行しない。
