# エラー時の診断記録ポリシー

> 作成日: 2026-11-19
> 更新日: 2026-11-19
> 作成者: Codex

この文書は、Orchestratorとその補助ツールでエラーを調査・報告するときに、必要な診断情報を安全かつ過不足なく記録する共通方針を定めます。既存の構造化診断項目と保存先を優先し、すべての出力や実行環境を一律に採取することは求めません。

## 適用と基本原則

- エラーや失敗を調査・報告するときは、既存の構造化診断にある情報を使い、この文書の項目を可能な範囲で記録します。Git subprocessだけでなく、他のプロセス・処理段階で起きたエラーにも適用します。
- 原因調査に役立つ最小限の情報を選びます。平常時の詳細ログやstdout/stderr全文の採取は一律に追加せず、既存の記録機能・上限・プライバシー境界を尊重します。
- 値を取得できなかった項目は推測で埋めず、「未取得」「該当なし」などと区別します。事実、推論・仮説、未確認事項を分けます。

## 構造化して記録する項目

失敗イベントごとに、利用可能な範囲で次を記録します。

| 項目 | 記録する内容 |
|---|---|
| 記録形式 | 既存形式を使い、新形式を設ける場合は機械処理可能なフィールド名と値を使う。JSON / JSONLではスキーマまたは形式の版を識別できるようにする。 |
| 時刻 | 失敗を観測した日時。ISO 8601形式でUTC（Z）または明示したオフセットを付ける。 |
| 実行識別 | run IDと、別プロセスや複数イベントを結び付けるcorrelation ID。既存のrun IDで相関できる場合に別IDを重複発行しない。 |
| 処理段階 | 失敗した段階を示す安定した名前またはコード（例: push.secret-scan-and-whitespace-check）。 |
| 操作識別子 | 失敗したコマンドや処理の安全な識別子（例: git.diff.cached.check）。生のコマンド文字列、完全な引数列、秘匿値を含み得るパス・URL・ブランチ名は無条件に記録しない。 |
| 終了・例外 | 子プロセスの終了コードが取得できた場合はその値、例外が発生した場合は例外の型名。終了コードがない失敗では、ないことを明示する。例外メッセージやstack traceは安全性を確認せず転記しない。 |
| 出力の概要 | stdoutとstderrそれぞれについて、有無と長さを記録する。長さの単位（byteまたは文字）を一貫して定義し、採取上限による切り詰めがあればその状態も示す。内容自体は次節に従う。 |
| 安全な診断 | 秘密情報を除いた、原因切り分けに必要な短い診断内容。内容を安全に抽出できない場合は、分類、既知のreason code、または安全な短い要約に置き換える。 |
| 再現・調査 | 再現条件、実施した試行と結果、確認できた環境差分、未確認事項、残る不確実性。原因に関係すると判断した理由を、観測した事実と分ける。 |

既存の診断モデルが一部の項目（たとえば stage、reasonCode、exceptionType、exitCode、stdout/stderrの有無と長さ）をすでに構造化している場合は、その意味と命名を維持します。別のフィールドや別ログを重ねて作るのではなく、不足する情報だけを安全な方法で補います。

## 出力・秘密情報の安全な扱い

- 生のstdout、stderr、引数、環境変数、例外メッセージには、token、資格情報、契約本文、個人情報、リポジトリやユーザーの非公開パス等が含まれる可能性があります。ログへ書く前に、既知の秘密をマスキングし、必要性のない値を除去します。
- 失敗コマンドは許可されたコマンド識別子や操作コードで表します。生のコマンドラインを残す必要がある場合でも、許可された保存先・アクセス範囲で、秘密値を検査・除去した後に限ります。通常の診断ログには完全な引数列を残しません。
- stdout/stderrから残すのは、安全性を確認できた診断断片に限り、必要最小限にします。出力を切り詰める場合は長さと切り詰め状態を保持し、切り詰めた内容だけから原因を断定しません。
- 機密情報が混じる、または安全に除去できたと確認できない場合は本文を保存せず、既知のエラー分類・reason code、内容の長さ、必要に応じて適切なアクセス制御下でのハッシュ、または機密を含まない短い要約に置き換えます。ハッシュから秘密や本文を復元できないことを前提にし、低エントロピー値などハッシュ自体が情報を漏らす場合は記録しません。
- snapshot用Git index、一時作業領域、完全な差分などの生アーティファクトは無条件にログへ保存・添付しません。必要性と範囲を確認し、より小さく安全な参照情報で代替できない場合に限り、専用のアクセス制限付き領域へ別途保存します。通常の構造化診断には、有無・安全な識別子・ハッシュなど必要最小限を記録します。
- エラー記録の内容とアクセス権を確認し、run記録の閲覧・保管は調査に必要な担当者と運用者に制限します。認証情報や秘匿情報をログ本文に保存しないことを、アクセス制御の代わりにしてはいけません。

## 保存場所、保持、保存失敗

- 診断記録は既存のrun記録・イベント記録の保存先とライフサイクルに統合します。通常、checkoutに混入しないrun単位の記録領域を使います。追加の保存先が必要な場合は、その目的、所有者、アクセス制限、保持・削除条件を運用設定または関連文書で確認できるようにします。
- ログの保持期間は、既存のrun記録に設定された保持・削除方針に従います。無期限保存を新たに前提にせず、適用される保持方針を確認できない場合は、運用者へ確認・報告し、不要な複製や長期保存を避けます。
- 診断ログの書き込みに失敗しても、元の処理エラーを別のエラーで隠したり成功扱いに変えたりしません。既存機能が安全な最小情報を呼び出し元またはstderrへ返せる場合は、失敗段階、reason code、run/correlation ID等に限定して通知します。書き込み失敗自体も安全な分類で示し、保存できなかった項目と証跡の欠落を最終報告に明記します。
- 代替通知も機密を含まないよう確認します。保存失敗を理由にstdout/stderr全文やsnapshotを別経路へ無条件に複製してはいけません。

## 原因の評価と調査の終了

- 記録で確認した事実（実際のstage、コマンド識別子、終了コード、出力の有無・長さなど）と、そこから導いた推論・原因仮説を別々に示します。仮説には「仮説」「可能性」などのラベルを付け、根拠と未確認事項を併記します。
- 再現できない場合、実施した条件・試行・結果を記録し、「再現不可」とします。再現できなかったことだけで問題を解決済みとしません。
- 調査を終了したことと、受入条件を満たしたこと、Issueを解決・クローズしたことはそれぞれ別に記録します。原因が特定できなくても調査を終了する場合は、原因未特定の事実、受入条件の達成状況、残るリスク、必要な後続対応とIssueの状態を明示します。
