# Implementer / Reviewer の問題・対処報告方針

## 目的と適用範囲

この文書は、Implementer と Reviewer が作業中に遭遇した重要な問題を、確認できた事実と実施した対処に基づいて Orchestrator と指示者へ伝えるための方針を定めます。通常作業の逐次報告は増やさず、問題への対処、再試行、判断待ち、停止の理由を後から把握できることを目的とします。

ここで定めるのは報告内容・責務・頻度の指針です。報告スキーマ、保存先、イベント、ログ収集、再試行動作を新設・変更する仕様ではありません。既存機能が記録していると確認できない値を、記録済みとみなしてはいけません。

## 報告する事象と頻度

次のように、作業の判断や結果に影響する事象を報告します。

- 予期しないエラー、失敗、停止、タイムアウト、キャンセル、証跡・永続化の不整合
- 問題への修正・回避、再試行または再委譲を行ったとき
- 再試行の上限に達したとき、前提が満たせないとき、または追加判断が必要で停止するとき
- Reviewer が受け入れ条件に影響する指摘を見つけたとき
- 原因、実行結果、レビュー範囲などに重要な未確認事項が残ったとき

通常の進捗や成功した個々の操作はまとめて簡潔に伝えます。問題は、再試行・引き継ぎ・停止など次の判断より前に報告し、対処後に結果を更新します。同じ事象については一つの報告に追記・更新し、重要な新事実が出た場合に限り追加報告します。定期的な報告間隔や全操作の逐次記録は求めません。

## 報告項目

問題に関する報告では、分かる項目を簡潔に示します。該当しない項目や未取得の値は省略または「未取得」「不明」とし、推測で補いません。

| 項目 | 記載する内容 |
| --- | --- |
| 工程・役割 | 発生段階（例：準備、Implementer、Reviewer、修正、永続化・報告、公開）と担当役割 |
| 問題・分類 | 起きた問題と大まかな分類（例：入力検証、プロセス終了、timeout/cancel、レビュー指摘、永続化、公開、証跡不整合、不明） |
| 観測事実 | 観測した状態・エラー種別・終了コード・失敗した確認。確認した事実だけを書く |
| 実行条件・参照 | 利用可能な Run ID、attempt ID、commit SHA、契約や成果物のhash、OS・ランタイム等の安全な条件情報。存在する値だけを使う |
| 実施した操作 | 調査、修正、再試行、再委譲、停止など、実際に行った操作 |
| 結果 | 解決、未解決、部分解決、停止など。再試行ごとの回数と結果を区別する |
| 未検証事項 | 未確認の原因、未実施の検証、Reviewer が確認していない範囲など |
| 改善提案 | 再発防止や追加調査が有用な場合のみ、事実と区別して任意で記載する |

終了コードはプロセスから実際に取得できた場合に限り、対象プロセスとコードを記載します。timeout、停止要求、プロセス終了確認、出力stream切断、終了コード未取得は別の観測として扱い、互いに置き換えません。Reviewer の指摘には重要度、対象（ファイル・行など）、根拠を含め、未確認範囲も示します。

## 事実・推測・未確認の区別

「観測事実」「推測（原因候補）」「未確認」を見出しや明確なラベルで区別します。推測には、そう考える観測根拠と確度を添え、確認済みの原因のように記述しません。原因が分からない場合は「原因不明」とし、適切な停止や人間判断待ちを正常な結果として扱います。改善提案は推測とは別にし、可能性や条件を誇張しません。

## 役割の責務

- **Implementer**：作業中に起きた重要な問題、確認できた事実、試した対処・再試行と結果、残る未検証事項を報告します。原因の特定や修復ができない場合は無理に続行せず、必要な判断とともに停止します。
- **Reviewer**：重要な指摘とその根拠・重要度、確認した範囲と未確認範囲を報告します。指摘を記録し、修正の実施責任は負いません。追加修正が必要な場合は Orchestrator に返します。
- **Orchestrator**：役割ごとの報告と結果を集約し、許可された上限内での再試行、再委譲、指示者への確認、停止を判断します。各エージェントが観測していない事実や原因を作り足さず、Run の状態や元の結果を不当に成功へ変更しません。

## 機密情報と証跡

報告は必要最小限の要約と、必要に応じた証跡への安全な参照に留めます。認証情報、token、秘密鍵、機密性のある環境変数値、prompt/response本文、非サニタイズの生ログ・生例外・コマンド出力、内部推論の逐語記録を報告に含めず、新たに収集・複製しません。既存の保護・保存規則を緩和もしません。

診断に役立つ証跡を示すときは、アクセス制御された既存の保存先にあるイベントID、成果物ID、または許可されたパス等の参照と、安全な分類・状態だけを使います。証跡本文を報告へ貼り付けず、内容が機密か不明な場合は参照を共有せず、その旨を報告します。参照IDや実行条件も、秘密や不要な個人情報を含まないことを確認してから記載します。

## Issue #49 Diagnostic Agent との境界

Issue #52 は作業中の役割が問題・対処・結果を適時に伝えるための方針です。将来の Diagnostic Agent（Issue #49）は異常終了後に独立して起動し、許可された証跡を読み取り専用で分析して、根拠・事実・原因候補・不足情報・改善提案を別の診断レポートへまとめる構想です。Diagnostic Agent は Implementer/Reviewer の報告責任を置き換えず、今回の変更で実装・起動・自動修復は行いません。

将来の接続に備え、既に安全に得られる範囲で、次の診断材料を報告項目に含めます。

- 工程・役割と問題の大まかなエラー分類
- 実測した終了コード、timeout/cancel、プロセス終了確認、stream切断など、取得できた終了状態
- Run/attempt、commit・契約・成果物hashなどの安全な参照IDと、OS・ランタイム等の関連条件
- 実施した再試行・再委譲と各結果
- 未検証事項、原因候補とその根拠
- 機密を含まない既存証跡への参照（イベント・成果物ID等）と、その所在が確認できない場合の明示

これは将来の Agent 向け入力契約でも、現行の全値を記録する保証でもありません。Issue #49 が想定する既存のイベント、報告、Agent応答・実行証跡、workspace snapshot、公開処理の安全な段階・理由コードなどを、後続設計で許可リストとサニタイズ境界に沿って選別する際の指針です。生ログや未加工のAgent応答を診断入力へ自動投入する許可にはなりません。利用可能な安全な証跡がないときは不足として示し、元のRun結果と証跡を変更しない読み取り専用診断の境界を維持します。

## MVP における扱い

今回定めるのは方針文書だけです。実行時の報告形式・イベント・schema、追加ログ、保持期間、機密フィルタ、再試行ロジック、Diagnostic Agent の実装は別の判断と作業が必要です。既存機能で安全に参照できる情報だけを使い、存在しない機能を前提にしません。
