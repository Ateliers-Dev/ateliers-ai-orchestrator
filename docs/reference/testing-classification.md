# テスト種別と責務

> 作成日: 2026-11-20
> 更新日: 2026-11-20
> 作成者: Codex

この文書は、テストを利用する外部依存と検証する責務で分類する規約です。テスト名やプロジェクト名だけでなく、実際に何を置き換え、何を成功条件にしているかを基準にします。

## 最優先の開発原則

> **マイルストーンの完遂より、Ateliers 開発プロセスの成熟を優先します。**

テストを通すためだけの変更ではなく、原因・判断・再発防止を記録し、後続の開発者やAIエージェントが再利用できる工程と構造を整えます。

## 分類

| 種別 | 対象 | 成功条件の例 |
|---|---|---|
| **UnitTests** | 外部プロセスや外部サービスを使わず、個々の内部ロジックを検証する。依存は値・インメモリの代替に置き換える。 | 入力値を与えたときの解析結果、検証結果、状態判定、整形結果 |
| **FakeTests** | Fakeを使い、コンポーネント間の決定論的なデータ受け渡し、状態遷移、異常系、証跡の生成・引き渡しを検証する。 | Fakeが受け取った要求の内容、呼び出し回数、記録された状態・証跡、不正応答への処理 |
| **IntegrationTests** | 実際の外部システム・ツール・サービスとの接続、通信、実行完了を検証する。高コストまたは副作用のある接続は明示opt-inにする。 | 実プロセスを起動して応答を受信できた、実APIが要求を受け付けた、接続先との処理が完了した |

テストプロジェクトとディレクトリは、この分類に対応させます。個々のテストも、そのテストが属する責務が明確になるよう分割します。異なる分類の検証を一つのテストに混在させません。

## AIエージェントを接続するIntegrationTests

- 実AIは非決定的な外部システムとして扱います。
- 実Codex IntegrationTestでは、実行プロセスの起動、通信の成立、応答の受信、異常終了せずに呼び出しが完了したことを確認します。必要なら応答が空でないことなど、応答が到達した事実だけを確認します。
- 自然言語の語句、判断の正しさ、指示追従、回答品質、特定の形式や期待文言の再現を合否条件にしません。モデルごとの性能評価・信頼性評価は別責務です。
- 実AI IntegrationTestに、Fakeで決定論的に確認できる入力構築、パラメータ受け渡し、解析、状態遷移、証跡保存を重ねません。
- 外部接続完了を示すために必要な最小限の検査に絞ります。応答内容の評価が必要になった場合はFakeTestsへの移行または別のモデル評価として整理します。

## Slack通知のテスト境界

- UnitTestsとFakeTestsはSlack実APIへ接続しません。FakeTestsからCLIの `run` を起動する場合は通知を `disabled` にし、配送処理を検証するときはFake送信者を使います。
- Slack実APIへの送信を確認するテストは、専用の明示opt-in IntegrationTestに分けます。Orchestratorのライフサイクル通知テストは `ATELIERS_RUN_ORCHESTRATOR_SLACK_INTEGRATION_TESTS=1` が設定されたときだけFake Stopシナリオを実行し、設定された `testChannelId` へ送信します。
- Slackテスト用opt-inは通常のUnit/Fakeテスト実行やCodex IntegrationTestを有効化せず、実送信対象のIntegrationTestだけに適用します。

将来、自律マージ機能を実装する場合、その分岐は固定したFake応答・品質ゲート結果を使い、マージ要求の有無、最終状態、理由・証跡の記録をUnitTests/FakeTestsで決定論的に検証します。これはMilestone 1の必須受入条件ではありません。実Codexにモデル判断をさせて分岐を試験したり、実GitHubマージを行ったりすることは、分岐制御のテスト条件にしません。

## 境界の決め方

1. 検証対象の依存先を列挙し、実物を使用するかFake等に置き換えるかを確認する。
2. 何を確定的に証明するテストかを一文で書く。
3. Fakeで確認できるプログラム上の振る舞いはUnitTestsまたはFakeTestsに置く。
4. 実IntegrationTestsは実接続が必要な確認に限定し、AIの意味内容や品質を判定しない。
5. 一つのテストが複数の責務を持つ場合は、分類に合わせてテストを分割する。

## 通常PRの必須品質ゲート

- `UnitTests` と `FakeTests` はどちらも通常PRの必須ゲートです。該当するプロジェクト内のテストを実行し、両方の全件成功を確認します。一方の成功で他方を代替できません。
- 結果未確認または未実行のUnit/Fakeプロジェクトがある場合、通常PRの必須ゲートは未達です。
- 外部システムへの実接続が必要な `IntegrationTests` は通常PRで一律必須にしません。Issue、受入条件、変更リスク等が求めるときに別途実行します。IntegrationTestsの実行要件がある場合も、Unit/Fakeの必須ゲートは維持します。
- CIはUnitTestsとFakeTestsの分類別プロジェクトを実行対象に含めます。ローカルの実行方法はリポジトリの `AGENTS.md` と該当workflowを参照してください。

具体的な現行テストの棚卸しと今回の是正内容は、[Issue #79 テスト分類見直し記録](../issues/issue-79-test-classification-review.md)を参照してください。

ローカルGit CLIを使う決定論的な回帰テストの分類と、変更時に維持する過去障害の対応表は[Git安全性の回帰対策](git-safety-regressions.md)を参照してください。
